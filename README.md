# Transaction Ledger API

Backend-only transaction ledger built with Node.js, TypeScript, Express, PostgreSQL, Prisma, and Zod. It creates accounts, applies credits and debits atomically, reports balances and paginated history, and supports atomic transfers.

## Requirements

- Node.js 20 or later and npm
- PostgreSQL 14 or later

## Run locally

1. Install dependencies: `npm install`
2. Create a PostgreSQL database named `ledger_db` (or choose another database).
3. Copy `.env.example` to `.env` and set `DATABASE_URL` and `PORT`.
4. Generate Prisma Client and apply migrations: `npm run db:generate` then `npm run db:deploy`.
5. Start in development with `npm run dev`, or compile and run using `npm run build` and `npm start`.

The API listens on `http://localhost:3000` by default. Interactive Swagger documentation is at `/docs`; its source specification is in `docs/swagger.json` and is served through the Swagger UI. Import `postman/Transaction-Ledger.postman_collection.json` into Postman to try the API. The collection includes success cases and validation, duplicate, insufficient-funds, filtering, pagination, and transfer examples.

We can access the swagger docs by following the step below:

Start the API with `npm run dev`, then open http://localhost:3000/docs in your browser. Swagger UI loads the API spec from `docs/swagger.json`

## Endpoints

| Method | Path                                                      | Behavior                                     |
| ------ | --------------------------------------------------------- | -------------------------------------------- |
| GET    | `/health`                                                 | Service/database health check                |
| POST   | `/accounts`                                               | Create an account; body: `{ "name": "Ada" }` |
| GET    | `/accounts/{id}`                                          | Get account details                          |
| GET    | `/accounts/{id}/balance`                                  | Get current balance                          |
| POST   | `/accounts/{id}/transactions`                             | Create a credit or debit                     |
| GET    | `/accounts/{id}/transactions?type=credit&page=1&limit=10` | Filtered, latest-first paginated history     |
| POST   | `/transfers`                                              | Atomic transfer between two accounts         |

Transaction body example:

```json
{
  "type": "credit",
  "amount": 25.5,
  "description": "Invoice payment",
  "reference_id": "invoice-001"
}
```

Amounts must be positive numbers with at most two decimal places. `reference_id` is unique per account. Repeated references produce `409 Conflict`; insufficient debit balance produces `422 Unprocessable Entity`. Validation errors use `400`, missing accounts use `404`, and errors share `{ "error": { "code": "...", "message": "..." } }`.

History returns `current_page`, `page_size`, `total_records`, `total_pages`, and `data`. `type` may be `credit` or `debit`; omit it for all transaction types. Page must be at least 1 and limit is 1–100.

## Integrity and assumptions

- Account IDs, transaction IDs, and timestamps are generated by PostgreSQL/Prisma. Client-supplied account balances are rejected; new accounts start at zero.
- Balances use PostgreSQL `DECIMAL(14,2)`. The account row is locked during ledger writes, all balance and transaction changes share a database transaction, and transfer locks are acquired in account-ID order.
- PostgreSQL constraints enforce nonnegative balances, positive transaction amounts, valid transaction types, foreign keys, and per-account reference uniqueness. A database trigger prevents transaction updates and deletes.
- Transfers create a debit and a credit transaction. Their references use `TRF-OUT-{reference_id}` on the source and `TRF-IN-{reference_id}` on the destination, allowing the same base reference in distinct accounts.
- The API assumes a trusted database role: direct out-of-band edits to account balances can bypass ledger service rules. The API itself exposes no update/delete transaction routes.
- No authentication or account ownership model is included because neither was part of the assignment requirements.

## Tests and code quality

The project is configured for Jest and Supertest (`npm test`) and ESLint/Prettier (`npm run lint`, `npm run format:check`). API integration tests require a disposable PostgreSQL database configured with `DATABASE_URL` and the migrations applied.
